# Число вызовов BLAKE3 update на чанк

Отдельный подсчёт по текущему `src/fused_stream_cdc.rs` на тестовом изображении (22 022 007 байт), за один полный проход. Считались внешние вызовы `Hasher::update`, а не внутренние сжатия BLAKE3. Замер выполнен на временной копии модуля с обёрткой хешера, считающей все вызовы и отдельно вызовы с непустыми данными; алгоритм и исходные файлы проекта не изменялись. Время этой инструментированной версии не используется как результат производительности.

Batch — порог объёма ещё не переданных данных. Код проверяет его после фаз Gear, а не после каждого байта. На границе чанка остаток передаётся безусловно, затем выполняется finalize. Отдельный накапливающий буфер размером batch не выделяется: передаются срезы уже имеющегося буфера.

В 4/16/64 встречаются два пустых финальных вызова update после передачи всего чанка. Поэтому при batch 32 и 64 KiB всего 1106 вызовов на 1104 чанка, хотя непустых обновлений ровно по одному на чанк. finalize выполняется отдельно один раз на чанк и в update не включён.

При 50 одинаковых обработках суммарные количества умножаются на 50, а среднее на чанк остаётся тем же. Параметр avg — целевая настройка FastCDC, а не фактическая средняя длина: на этом входе получено 1987 чанков для 4/8/64 и 1104 для 4/16/64.

Это подсчёт текущего исходника. Архивные perf-логи не содержат числа update и не фиксируют точную версию бинарника; переносить эти числа на исторические замеры как непосредственно измеренные тогда нельзя.
